# TikFinity ミニゲーム(ガチャ・ルーレット)

TikTok LIVE のギフトに反応して、配信画面にガチャやルーレットを表示するミニゲームです。
抽選結果は「ハートピアでの行動・縛りチャレンジ」などの文言として表示します。
PC は不要で、iPhone / iPad のブラウザだけで設定・運用できるように作っています。

```
視聴者がギフトを送る
  → TikFinity(iPhone)が Webhook を送信
  → Cloudflare Worker が受信:重複チェック → 設定と照合 → 抽選(ここで1回だけ確定)
  → Firebase Realtime Database の「再生待ちキュー」に追加
  → 表示画面(PRISM LIVE)が届いた順に1件ずつ再生
```

## できること

- ギフトごとに「ガチャ」か「ルーレット」を割り当てる
- ギフトごとに 有効/無効・抽選テーブル・画面に出すタイトル・連続ギフト(コンボ)時の扱い を設定する
- 抽選テーブルごとに 候補・重み(当たりやすさ)・レア度 を設定する(確率は自動計算)
- 複数のギフトが続けて届いても、届いた順に最後まで1件ずつ再生する
- 表示画面を読み込み直しても、続きから再生する(二重再生・取りこぼしなし)
- 同じイベントが2回届いても1回分として扱う
- 本番用とテスト用のデータを完全に分ける(URL の `?env=prod` / `?env=test`)

## ページ一覧

| ページ | 役割 | 開く場所 |
|---|---|---|
| `display.html?env=prod` | 表示画面(背景透明・9:16) | PRISM LIVE |
| `admin.html` | 管理画面(ギフト・抽選テーブル・受信ログ) | iPhone / iPad の Safari |
| `test.html` | テスト画面(疑似ギフト送信・キュー確認・プレビュー) | iPhone / iPad の Safari |
| `index.html` | ページ一覧 | どこでも |

`?env=` を付けない場合はすべて **テスト** になります(本番を誤操作しないため)。

## セットアップ

所要時間の目安は 30〜60 分です。上から順に進めてください。

### 1. GitHub Pages を有効にする

1. このリポジトリの **Settings → Pages** を開く
2. **Source** を「Deploy from a branch」、**Branch** を `main` / `/(root)` にして保存
3. 数分後に `https://<ユーザー名>.github.io/tikfinity-minigame/` で開けるようになる

### 2. Firebase プロジェクトを作る(新規)

1. [Firebase コンソール](https://console.firebase.google.com/) で新しいプロジェクトを作成(Google アナリティクスは不要)
2. **構築 → Realtime Database → データベースを作成**
   - ロケーションはどこでも可。「ロックモードで開始」を選ぶ
   - 作成後に表示される URL(`https://〜.firebaseio.com` または `https://〜.firebasedatabase.app`)を控える
3. **ルール** タブを開き、このリポジトリの [`database.rules.json`](database.rules.json) の中身をすべて貼り付けて **公開**
4. **プロジェクトの設定(歯車)→ 全般 → マイアプリ → ウェブ(</>)** でアプリを登録
   - 表示される `firebaseConfig` の値を、GitHub 上で [`js/config.js`](js/config.js) を編集して貼り付ける
     (`apiKey` `authDomain` `databaseURL` `projectId` `appId` の5つ)
   - この値はブラウザに公開される前提のもので、秘密情報ではありません
5. **プロジェクトの設定 → サービスアカウント → 新しい秘密鍵を生成** で JSON ファイルをダウンロード
   - この中の `client_email` と `private_key` を次の手順で使います
   - **このファイルは誰にも見せず、GitHub にも置かないでください**(データベースを自由に書き換えられる鍵です)

### 3. Cloudflare Worker を作る

1. [Cloudflare](https://dash.cloudflare.com/) にログイン(無料プランで可)
2. **Workers & Pages → 作成 → Worker を作成**(名前は例: `tikfinity-minigame`)→ デプロイ
3. **コードを編集** を開き、中身をすべて消して [`worker/dist/worker.js`](worker/dist/worker.js) の中身を貼り付け → **デプロイ**
4. Worker の **設定 → 変数とシークレット** で、次をすべて「シークレット」として追加

   | 名前 | 値 |
   |---|---|
   | `FIREBASE_DB_URL` | 手順2-2で控えたデータベースの URL |
   | `SA_CLIENT_EMAIL` | 秘密鍵 JSON の `client_email` |
   | `SA_PRIVATE_KEY` | 秘密鍵 JSON の `private_key`(`-----BEGIN PRIVATE KEY-----` から `-----END PRIVATE KEY-----\n` まで全部) |
   | `WEBHOOK_KEY` | TikFinity の URL に付ける合言葉(長めのランダムな英数字) |
   | `ADMIN_KEY` | 管理画面・テスト画面用の合言葉(`WEBHOOK_KEY` とは別のもの) |
   | `DISPLAY_KEY_PROD` | 本番の表示画面(PRISM に設定する URL)に付ける合言葉(ほかの合言葉とは別のもの) |
   | `DISPLAY_KEY_TEST` | テストの表示画面に付ける合言葉(`DISPLAY_KEY_PROD` とは別のもの) |
   | `ALLOWED_ORIGIN` | (任意)`https://<ユーザー名>.github.io` を入れると、他のサイトから管理APIを呼べなくなる |

5. Worker の URL(`https://tikfinity-minigame.〜.workers.dev`)をブラウザで開き、`{"ok":true,...}` と出れば OK

> コードを更新したときは、手順3-3 をやり直してください。

### 4. 管理画面で設定する(まずはテスト用)

1. `admin.html` を開く(上部が「テスト」になっていることを確認)
2. **接続設定** に Worker の URL・`ADMIN_KEY`・表示用の合言葉(本番・テスト)を入れて保存(この端末のブラウザにだけ保存されます)
   - URL は `https://〜.workers.dev` まで(後ろに `/` 以降を付けない)
   - `js/config.js` の `DEFAULT_WORKER_URL` に書いておくと、URL の入力は省略できます
3. **接続テスト** を押し、すべて ✓ になることを確認(✗ の項目に原因と直し方が表示されます)
4. **サンプルを読み込む** → 内容を編集 → **保存**

### 5. テスト画面で確認する

1. `test.html` を開き、「表示画面のプレビュー」をオン
2. 「1件送信」「5人から連続で送信」「同じギフトを2回送信(重複テスト)」で動きを確認
3. 本物の表示画面で確認したい場合は、管理画面の「URL の案内」の表示画面の URL(テスト)を別の端末やタブで開く(右上に TEST と出ます)

### 6. TikFinity から Webhook を送る

1. TikFinity の **Actions & Events** で、Webhook を送るアクションを作る
2. 送信先 URL に次を設定(管理画面の「URL の案内」からコピーできます)
   ```
   https://<Worker の URL>/webhook?env=test&k=<WEBHOOK_KEY>
   ```
   - `env=test`(テスト)か `env=prod`(本番)は**必ず付けてください**。省略すると Worker は受け付けず(400)、どちらの環境にも書き込みません
3. ギフトを受け取った時にそのアクションが実行されるよう、イベントを設定
4. 実際にギフトを送ってもらい(または TikFinity のテスト機能で)、管理画面の **受信ログ** を確認
   - どんな項目名(`giftName` など)で届いているか
   - ギフト名が何語で届いているか(管理画面のギフト名はこれと完全一致させる)
   - 連続ギフトのとき、Webhook が「途中で何回も」届くのか「最後に1回」なのか

> **要確認**:iPhone の TikFinity アプリで Webhook アクションが使えるかは、このリポジトリでは確認できていません。
> 受信ログに何も出ない場合は、TikFinity 側の設定・対応状況を確認してください。

Worker が理解できる項目名は次のとおりです(form 形式・JSON・URL のクエリのどれでも可)。
これ以外の名前で届く場合は [`shared/core.js`](shared/core.js) の `normalizeGift` に候補名を足します。

| 用途 | 受け付ける項目名 |
|---|---|
| ギフト名(必須) | `giftName` `gift_name` `giftname` |
| 個数 | `repeatCount` `repeat_count` `repeatcount`(無ければ1) |
| 送った人の表示名 | `nickname` `displayName` `username` `uniqueId` `userId` |
| 一意なID(重複判定) | `msgId` `msg_id` `messageId` `eventId` `event_id` |
| コンボ確定 | `repeatEnd`(`false` の時は途中経過として無視) |

### 7. PRISM LIVE に表示画面を追加する

1. まず見本で大きさを合わせる。PRISM LIVE で Web(ブラウザ)ソースを追加し、URL に次を設定
   ```
   https://<ユーザー名>.github.io/tikfinity-minigame/display.html?demo=1
   ```
   見本のガチャ・ルーレットが繰り返し再生され、左下に表示領域の大きさが出ます
2. Web ソースの **幅・高さを縦長の大きいサイズ(例 1080×1920)** にする
   - 左下に「⚠ 横長です」「⚠ 小さく描画されています」と出たら、幅・高さを見直す
   - 幅・高さが小さいと、小さく描いたものを引き伸ばすことになり、文字がぼやけます
3. 文字がはっきり見えるようになったら、URL を管理画面の「URL の案内」の表示画面の URL に変える
   ```
   https://<ユーザー名>.github.io/tikfinity-minigame/display.html?env=prod&dk=<表示用の合言葉>&…
   ```
   - `dk=` の合言葉が入った URL なので、配信画面や人に見せないでください
4. カードの縦位置は `&top=300` のように調整できます(1080×1920 基準の px)。背景は透明です

> **要確認**:iPad の PRISM LIVE「画面配信」モードで Web ソースを重ねられるかは未確認です。

### 7-2. デザイン・位置・大きさを調整する

管理画面の **表示の調整** で、次をプレビューを見ながら決められます。設定は**デザインごとに別々**に保存されます。

- デザイン(従来 / 和風)
- ガチャ・ルーレットそれぞれの台紙の上端の位置と大きさ
- コメント欄よけ(オンにすると、台紙がこの線より下に出ないよう自動で小さくします。結果が2件並んでも越えません)
  - 和風などの画像デザインでは、縮めたぶん結果の文字(結果の一覧・札・結果枠)を最大1.3倍まで大きくして、読みやすさを保ちます
- 和風などの画像デザインでは、半透明の台紙を出すかどうか

| デザイン | 初期値 |
|---|---|
| 従来 | 上端 300px・大きさ 100%・コメント欄よけ なし(以前と同じ表示) |
| 和風 | 上端 110px・大きさ 100%・コメント欄よけ 1100px(暫定)・台紙あり |

下に表示される URL を PRISM LIVE の Web ソースに設定してください。

> 設定は管理画面を開いた端末のブラウザと、表示画面の URL に入ります(Worker・Firebase には保存しません)。
> 調整を変えたら、PRISM の URL も貼り直してください。
> TikTok のコメント欄の高さは端末やコメント数で変わります。実際の配信画面を見て、コメント欄よけの線を合わせてください。

### 8. 本番に切り替える

1. 管理画面(テスト)で **テスト → 本番にコピー**
2. TikFinity の Webhook URL の `env=test` を `env=prod` に変更
3. PRISM LIVE の表示画面が本番用の URL(`?env=prod&dk=…`)になっていることを確認

### 9. 表示画面の再生担当(同時に再生するのは1つだけ)

同じ環境(本番・テスト)で再生する表示画面は**1つだけ**です。最初に開いた表示画面が「再生担当」になり、
ほかの表示画面は待機します(待機中は何も映しません。`&debug=1` を付けると「待機中」と出ます)。

- 担当の画面が動いているあいだ(10秒ごとに Worker に応答)は、別の画面を開いても担当は移りません
- 担当の画面を閉じる・再読み込みすると、待たずに担当が空く/同じ画面が担当に戻ります
- 担当の画面が落ちて応答が30秒途絶えると、待機中の画面が引き継ぎます
- 別の表示画面に切り替えたいときは、管理画面の **表示画面の再生担当 → 再生担当を外す**。
  待機中の画面が10秒ほどで引き継ぎます(外された画面は30秒間は担当に戻りません)
- 再生位置は担当の画面から Worker 経由でだけ保存されます(ブラウザから Firebase へは書き込めません)。
  Worker に届かないあいだも再生は続け、保存はやり直し続けます。30秒以上届かない場合は、二重再生を避けるため新しい再生を止めて待ちます
- 本番とテストは、合言葉・担当・再生位置がすべて別々です

#### 制限事項(知っておくこと)

| 場面 | 起きること | 対処 |
|---|---|---|
| 管理画面で「再生担当を外す」を押したが、待機中の表示画面が無い | 外された画面は30秒間担当に戻れないため、**最大30秒ほど再生が止まります**。その間に届いたギフトは、再開後に順番どおり再生されます | 切り替え先の表示画面を先に開いてから外す |
| 担当の表示画面が落ちた・ネットが切れた(ページを閉じる処理が動かなかった) | 応答が30秒途絶えて期限切れになるまで、ほかの画面は引き継げません。待機中の画面の確認間隔と合わせて、**最大40秒ほど**かかります | 急ぐときは管理画面の「再生担当を外す」 |
| PRISM LIVE で Web ソースを再読み込みした | 通常は待たずに担当へ戻ります(閉じる時に担当を降りる/前回の token で戻る)。PRISM がブラウザを作り直して両方とも効かなかった場合は、上と同じく最大40秒ほど待ちます | 待てない場合は管理画面の「再生担当を外す」 |
| 同じ環境の表示画面を複数開いた(PRISM と別タブなど) | 最初に担当になった画面だけが再生し、ほかは待機して何も映しません。どの画面が担当かは画面上では分かりません | 管理画面の「表示画面の再生担当」で確認。`&debug=1` を付けると待機中の画面に「待機中」と出ます |
| 同じタブを複製した | 複製したタブも同じ画面 ID を持ちますが、担当に戻るたびに token が新しくなるため、担当になれるのはどちらか一方だけです | 不要なタブを閉じる |
| Worker に届かない状態が30秒以上続いた | 二重再生を避けるため、新しい再生を止めて待ちます(再生中のものは最後まで再生)。復旧すると未再生分を順番どおり再生します | Worker の状態を確認 |
| Firebase のルールを新しくした後、`dk=` の無い古い URL のまま | 再生はしますが再生位置を保存できず、再読み込みすると同じものを再生することがあります | 「URL の案内」から URL をコピーし直す |
| 表示画面の URL(`dk=` 入り)が漏れた | その URL を知っている人は、担当が空いた時に担当になれます(勝手に担当を奪うことはできません) | Worker の `DISPLAY_KEY_PROD` / `DISPLAY_KEY_TEST` を変えて、URL を貼り直す |

- 表示用の合言葉は、管理画面を開いた端末のブラウザ(localStorage)に保存されます(管理用の合言葉と同じ扱い)。管理画面の画面上では伏せて表示し、コピーボタンでだけ合言葉入りの URL を取り出せます
- 表示画面は Referer で URL の合言葉をほかのサイトへ送らないようにしています(`<meta name="referrer" content="strict-origin">`)
- 担当の状態(`state/display/player`)は誰でも読めますが、含まれるのは画面 ID と token のハッシュだけで、ハッシュから token は求められません

### 10. 再生担当への切り替え手順(Worker 1.2 以前から更新する場合)

**順番を守ってください**(先にルールを変えると、古い表示画面が再生位置を保存できなくなります)。

1. **Worker**
   1. Cloudflare の Worker に、シークレット `DISPLAY_KEY_TEST` と `DISPLAY_KEY_PROD` を追加(長めのランダムな英数字。2つは別の値)
   2. 最新の [`worker/dist/worker.js`](worker/dist/worker.js) を貼り付けてデプロイ
   3. 管理画面の「接続テスト」で、Worker のバージョンが 1.3.0、シークレットが「すべて設定済み」になることを確認
   4. TikFinity の Webhook URL に `env=test` / `env=prod` が付いていることを確認(1.2.0 以降、付いていないと受け付けません)
   - この時点では古い表示画面もそのまま動きます(Firebase のルールがまだ古いため)
2. **ページ(GitHub Pages)** を更新する(main に反映)
3. **テストで確認**
   1. 管理画面(テスト)の「接続設定」に表示用の合言葉(本番・テスト)を入れて保存
   2. 「URL の案内」の表示画面の URL(テスト)を PRISM か別のタブで開く
   3. 管理画面の「表示画面の再生担当」が「担当あり」になること、テスト画面から送ったギフトが再生され「再生済み」になることを確認
   4. 2つ目の表示画面を開いても再生されないこと、「再生担当を外す」で切り替わることを確認
4. **本番の表示画面の URL を差し替える**:PRISM LIVE の Web ソースの URL を、「URL の案内」の本番用(`dk=` 付き)に変える
5. **Firebase のルール**:Firebase コンソール → Realtime Database → ルール に、最新の [`database.rules.json`](database.rules.json) を貼り付けて公開
   - これでブラウザから `state/display` に書き込めなくなります
   - ルールを公開した後は、`dk=` の無い古い URL の表示画面は再生位置を保存できません(再生はしますが、再読み込みすると同じものを再生することがあります)

#### 元に戻す(ロールバック)

切り替えと**逆の順番**で戻します。

1. **Firebase のルール**:1つ前のルール(このリポジトリの履歴で、`state/display` に `.write` がある版。例: `git show c32abe6:database.rules.json`)を貼り付けて公開
2. **ページ**:GitHub で main を切り替え前の版に戻す(revert)。古いページは `dk=` を無視して Firebase に直接保存するので、PRISM LIVE の URL は `dk=` 付きのままでも動きます
3. **Worker**:切り替え前の `worker/dist/worker.js`(例: `git show c32abe6:worker/dist/worker.js`)を貼り付けてデプロイ。追加したシークレット `DISPLAY_KEY_*` は残っていても害はありません
   - ページより先に Worker を戻すと、新しいページが担当になれず再生が止まります。必ずページの後に戻してください
- Firebase の `state/display` に残る `player` `released` の項目は、古い表示画面が再生位置を保存する時に上書きされて消えるので、手で消す必要はありません

## 設定項目の説明

### 連続ギフト(コンボ)のとき

| 設定 | 動き | 例(バラ×5) |
|---|---|---|
| 何個でも1回だけ抽選 | 個数に関係なく1回 | 1回 |
| 個数ぶん抽選 | 個数と同じ回数(上限あり) | 5回 |
| N個ごとに1回抽選 | 個数÷N 回(端数切り捨て、上限あり) | N=2 なら2回 |

複数回の場合、表示画面では「1 / 5 回目」のように1回ずつ再生し、結果を下に並べていきます。

### 全体設定

- **古い未再生イベントを飛ばす(分)**:表示画面を長く閉じていた後に開いた時、古いものまで再生しないようにする
- **重複とみなす間隔(秒)**:TikFinity が一意な ID を送ってこない場合の重複判定。同じ人・同じギフト・同じ個数がこの秒数以内に届いたら1回分として扱う

### 表示画面の URL オプション

| パラメータ | 意味 |
|---|---|
| `env=prod` | 本番のキューを再生(省略時はテスト) |
| `skip=1` | 起動時に溜まっている未再生分を飛ばす |
| `speed=2` | 演出の速さ(確認用) |
| `demo=1` | 見本を繰り返し再生(Firebase に接続しない)。`demo=gacha` / `demo=roulette` で片方だけ |
| `theme=wafu` | 画像テーマ(`images/themes/<名前>/`)。省略時は従来のデザイン |
| `g=110,100` | ガチャの台紙の上端(px)・大きさ(%) |
| `r=110,100` | ルーレットの台紙の上端(px)・大きさ(%) |
| `safe=1100` | この高さより下に台紙を出さない(コメント欄よけ)。`safe=0` で使わない。画像テーマでは縮めたぶん結果の文字を最大1.3倍にする |
| `panel=0` | 画像デザインで半透明の台紙を出さない |
| `guide=1` | コメント欄の目安と safe の線を表示(調整用。配信には使わない) |
| `debug=1` | 表示領域の大きさ・倍率を左下に表示 |
| `soft=2` | 視聴者側で文字がギザギザに崩れる時の対策(1〜5)。配信用に縮小される前にごく軽くぼかす |

## 画像テーマの作り方・差し替え方

画像テーマは `images/themes/<名前>/` にまとまっています(例: `images/themes/wafu/`)。

| ファイル | 内容 |
|---|---|
| `theme.json` | 使う画像のファイル名、文字を置く位置、ルーレットの色、結果に添えるアイコンと言葉 |
| `theme.css` | 色・文字・配置 |
| `*.png` | 画像素材 |

- **同じファイル名で画像を上書きするだけ**で見た目が変わります
- 札(`card-frame`)の窓とリング(`roulette-ring`)の穴は、画像の**透明部分から自動で位置を測る**ので、比率が変わっても `theme.json` の修正は原則いりません
- 札・結果枠は画像の縦横比のまま表示します
- 結果枠・タイトル帯の文字の位置だけは、飾りの形によって `theme.json` の `resultText` / `titleText`(%)で調整します
- 札は `theme.json` の `cardWiden` で(暫定。横幅の広い専用の札の画像ができたら差し替えます)、飾りの無い縦の帯(`stretch`、画像の幅に対する %)だけを引き伸ばして横に広げています(`aspect` は広げた後の幅÷高さ)。最初から横長の札の画像に差し替えるときは `cardWiden` を消してください。`cardTextSide` は札の文字が左右の飾りに掛からないよう空ける幅(元の画像の幅に対する %)です
- 当選時の演出はレア度ごとに `theme.json` の `effects` で決めます。`glow`(中央の光)・`aura`(札・結果枠のふちの光)・`rays`(光の筋)は 0〜1、`sakura`(花びらの数)・`gold`(金の粒の数)は個数、`duration` はミリ秒(最大2500)、`color` は光の色です。演出は台紙の中の演出の場所だけに出て、時間がたつと消えます。表示画面の URL に `demo=gacha&rarity=SSR` を付けると、レア度ごとの演出を確認できます
- レア度の色は `theme.json` の `rarityColors`(和風は N 灰・R 緑・SR 紫・SSR 金)で、結果一覧・バッジ・札のふちの線・演出の光が同じ色になります。`badgeStyle: "text"` のあいだはバッジを HTML で描きます(色に合ったバッジ画像ができたら `"image"` にすると画像に戻ります)
- 送信者名・ギフト名・結果・レア度・件数などの文字は、画像に焼き込まず HTML の文字で重ねています

画像素材の注意:

- 背景は完全に透明にする(元画像の背景色を残さない)
- 周りに少し余白を取り、ほかの素材の一部が入らないようにする
- 札の窓・リングの穴は透明にする(ここに文字や盤面が表示されます)

## データの持ち方(Firebase Realtime Database)

```
/envs/{prod|test}/
  config/                  設定(管理画面から Worker 経由で保存)
    gifts/{ギフト名を変換したキー}  { giftName, enabled, mode, tableId, title, combo, comboN, maxRolls }
    tables/{tableId}       { title, items: [{ label, weight, rarity, color }] }
    settings               { staleMinutes, dedupeWindowSec }
  queue/{pushId}           再生待ち(Worker が抽選済みの結果を追加。最新300件を保持)
                           { giftName, sender, repeatCount, mode, title, rolls[], pool[], receivedAt, source }
  state/display            { lastPlayedKey, updatedAt, player, released }  どこまで再生したか・再生担当
                           player: { id, tokenHash, gen, since, expiresAt }(Worker だけが書き込む)
  dedupe/{hash}            重複判定用の受信時刻(24時間で削除)
  log/{pushId}             受信ログ(最新100件を保持)
```

- 書き込みは Worker(サービスアカウント)だけが行います。ブラウザからはどこにも書き込めません
  (表示画面の再生位置も、表示用の合言葉を持つ再生担当の画面から Worker 経由で保存します)
- `config` `queue` `state` `log` は誰でも読めます(表示画面がログインなしで読むため)。
  受信ログには視聴者の表示名などが含まれます

## トラブルシューティング

| 症状 | 確認すること |
|---|---|
| 表示画面の右下に「js/config.js に〜」 | `js/config.js` の Firebase 接続情報 |
| 表示画面の右下に「Firebase に接続できません」 | ネット接続、`databaseURL` |
| 管理画面で保存できない・「Worker から応答を受け取れませんでした」 | 管理画面の「接続設定」→「接続テスト」で原因を確認。よくある原因: Worker が Hello World のまま(コードの貼り付け・デプロイ忘れ)、URL の間違い、`ALLOWED_ORIGIN` の値違い、シークレットの未設定 |
| 受信ログに何も出ない | TikFinity の Webhook URL(`k=` の合言葉・`env=`)、Worker の URL |
| 受信ログに「未設定のギフト」 | 管理画面のギフト名と、ログに出ているギフト名が完全一致しているか(ログの「このギフトを設定に追加」ボタンが便利) |
| 受信ログに「重複のため無視」が多すぎる | 全体設定の「重複とみなす間隔」を短くする(0 で無効) |
| 連続ギフトで何回も再生される | 受信ログで `repeatEnd` が届いているか確認。届かず途中経過も送られてくる場合は「何個でも1回だけ」にする |
| 視聴者側だけ文字がギザギザに崩れる | 表示画面の URL に `&soft=2` を付ける(足りなければ 3)。PRISM の画面はきれいでも、配信用に縮小される時に細い線が崩れることがあります |
| 配信画面で文字がぼやける・小さい | `display.html?demo=1` を開いて左下の表示を確認し、Web ソースの幅・高さを縦長の大きいサイズ(例 1080×1920)にする |
| 再生が溜まりすぎた | テスト画面の「キュー・ログを消去」、または表示画面を `&skip=1` 付きで開く |
| 表示画面に何も出ない(ほかの症状なし) | 別の表示画面が再生担当になっていないか。管理画面の「表示画面の再生担当」で確認し、必要なら「再生担当を外す」。`&debug=1` を付けると「待機中」と表示されます |
| 表示画面に「表示用の合言葉(dk)が URL にありません」「表示用の合言葉が違います」 | 管理画面の「URL の案内」から表示画面の URL をコピーし直す。Worker の `DISPLAY_KEY_PROD` / `DISPLAY_KEY_TEST` と管理画面の「接続設定」の値が一致しているか |

## 開発者向け

```sh
npm test                       # 単体テスト・Worker の結合テスト(偽の Firebase を使用)
npm run build                  # worker/dist/worker.js を生成(Worker のコードを変えたら必ず実行)
npm run check                  # worker/dist/worker.js が最新か確認(CI でも実行)
node tests/browser/smoke.mjs   # ブラウザでの動作確認(playwright が必要)
```

- `shared/core.js`:正規化・抽選・連続ギフト・重複判定・設定の検証(Worker とブラウザで共通)
- `worker/src/`:Worker 本体と Firebase REST クライアント
- `js/store.js`:ブラウザで Firebase を扱う唯一のファイル
- `js/api.js`:ブラウザから Worker を呼ぶ関数
- 外部ライブラリは Firebase の公式 SDK(CDN)のみで、ビルド工程はありません
